# D2 Process Diagrams

Load this guide only to create, revise, render, or review a process diagram. The contract defines locations, applicable roles, required extensions, and source-visualization relationships.

## Operation Boundaries

Classify the operation before running commands:

- **Permanent authorship:** creating a diagram, adjusting its appearance, or regenerating an accepted visualization changes governed content, even when process meaning is unchanged. Load `grill.md` and complete `authoring-context.md` before content analysis or authorship proposals. The human's explicit qualification and closed grill must cover the objective and affected files before any permanent write. An already closed grill may cover these operations within its approved scope; no separate interview is required per command. A new semantic decision or expansion of the affected set requires resuming the grill.
- **Read-only review:** inspect and report without a grill unless objective qualification is requested. For byte comparison, render only to a unique temporary SVG; use a temporary source copy if formatting is needed. Never format the permanent source or replace its visualization during review. A discrepancy is a finding, not permission to correct it.
- **Requested temporary export:** load `export.md` and follow its bounded exception. Model, format, validate, and render only temporary sources and derivatives. Permanent placement, component-set maintenance, and Markdown embedding rules below do not apply to an export. Never promote export adjustments to accepted wiki files.

## Model

- Canonical Markdown governs process meaning; D2 source and rendered SVG are complementary.
- Use canonical terms and the configured instance language for visible labels.
- Model roles or areas as neutral containers, with actions inside the responsible container.
- Use stable ASCII `snake_case` identifiers. Keep rare implementation comments concise and in the instance language.
- Use ovals for starts, ends, and milestones; rectangles for actions; diamonds for decisions; packages for subprocesses; circles for recurring rites; documents for relevant deliveries; and hexagons for convergence.
- Use solid directed edges for sequence and mandatory dependency; label decisions and non-obvious parallel, recurring, or informational edges.
- Do not encode semantics only through color. Explain every responsibility, condition, artifact, and exception needed for understanding in Markdown.

### Edge-label placement

Choose label placement during authorship from the relationship's canonical
meaning, not from an assumed rendered edge length:

- Use `source-arrowhead.label` for an outgoing decision condition, a triggering
  event, or information explaining why the source initiates the connection.
- Use `target-arrowhead.label` for information specific to the destination,
  such as cardinality at that endpoint.
- Use the main connection label for a description of the relationship as a whole
  with no privileged endpoint.

For example, place an outgoing decision condition near its source:

```d2
source -> target: {
  source-arrowhead.label: condition
}
```

Preserve the relationship's meaning and the required labels above. If canonical
Markdown leaves the label's semantic association ambiguous, return the decision
to the human rather than choosing by visual convenience. Keep
arrowhead labels short without losing conditions or other essential meaning;
if shortening requires a semantic decision, return it to the human. Arrowhead
labels do not receive the same automatic placement optimization as main
connection labels and can overlap surrounding elements, so review the rendered
SVG rather than assuming this syntax guarantees legibility. This anchors the
label near the endpoint; it does not set a maximum distance for the main label.

## Step Correspondence and Navigation

For permanent process diagrams, apply these requirements after consolidating
canonical Markdown:

- Associate every action, decision, and subprocess node with a specific canonical
  Markdown section describing that step. Its visible label must equal the section
  heading text, allowing only visual line wrapping. A matching title is not proof
  of matching meaning; resolve differences in responsibility, sequence, conditions,
  or scope with the human before aligning labels or adding links.
- Responsibility containers and auxiliary markers, such as start/end markers,
  need no separate section unless they have their own canonical description.
  They cannot replace the descriptions required for steps.
- Use stable identifiers for both the diagram node and the description target,
  independent of their visible titles. Keep node identifiers in ASCII
  `snake_case`; preserve target identity when titles change. Verify uniqueness
  in the relevant page and diagram context, including multiple diagrams on a page.
  Do not rely on incidental IDs generated by the SVG renderer.
- Make each step node clickable to its description, and provide a return link
  from that section to the corresponding node, not merely to the page or the
  whole diagram. Author outgoing links through D2's `link` attribute and return
  links in canonical Markdown. Use the consumer's supported anchor and viewer
  integration to resolve stable targets; do not assume a heading-derived slug
  stays stable after a rename.
- For navigation-only work, make the existing node itself clickable; add only
  the links and stable identifiers needed for navigation. Preserve visible labels,
  shapes, connections, styles, and layout. Do not add icons, buttons, symbols, or
  other visual elements merely to represent or activate a link. Adding navigation
  does not authorize redesign or correction of pre-existing discrepancies; report
  those separately and obtain approved scope before correcting them. Review any
  rendering-induced visual differences rather than silently accepting them.
- Repeated occurrences of the same step may point to the same canonical
  description and retain the same visible title. Give each occurrence its own
  stable node identifier and provide a separate return link to each occurrence.
- Standardize return-link text in the instance language. For a section with one
  return destination, use the localized equivalent of "Back to step in diagram".
  For multiple step destinations, use "Back to step in diagram: <node title>",
  reproducing the exact visible title apart from visual line wrapping. When
  same-title occurrences need disambiguation, use
  "Back to step in diagram: <node title> - <occurrence context>". Use meaningful
  context, including the diagram context when needed, rather than occurrence
  numbers alone. This context belongs in the return-link text, not in a renamed
  node label.

The association is mandatory regardless of the viewer. Interactive navigation
also requires viewer support: an SVG displayed as an ordinary Markdown image does
not activate its internal links. Preserve the configured Markdown visualization
embedding and validator compatibility. Do not replace it with raw HTML merely to
enable links, or hand-edit generated SVG. A viewer may enhance that embedding,
but its integration belongs to the consumer and requires authorized scope.

Verify the actual viewer's routing and target resolution rather than assuming
plain fragment links work. In a viewer such as Docsify, links must reach the
intended section or node without navigating to another entry accidentally. If
stable anchors or interactive embedding are unsupported, report the missing
capability and seek human disposition and an authorized integration follow-up;
do not claim bidirectional navigation is complete. A temporary static export
does not need interactive navigation and must not invent missing canonical
sections or change permanent content to obtain it.

## Render

Default to ELK, D2 theme 4, and vertical direction. Use horizontal direction only after rendered review finds vertical reading illegible, then keep it stable.

```bash
d2 themes
d2 fmt "<diagram>.d2"
d2 fmt --check "<diagram>.d2"
d2 validate "<diagram>.d2"
d2 --bundle=true --theme=4 --layout=elk "<diagram>.d2" "<diagram>.svg"
```

Confirm theme 4 is Cool Classics in the installed D2 version. Render only after formatting and validation pass. Never edit generated SVG manually.

The formatting and rendering commands write files. Use permanent paths only under approved permanent authorship; otherwise use the temporary paths permitted by the classified operation.

## Review

- Compare labels, owners, decisions, merges, and links against canonical Markdown.
- Review [step correspondence and navigation](#step-correspondence-and-navigation):
  inventory missing or ambiguous associations, differing titles, unstable targets,
  and absent or broken links in either direction. Report semantic discrepancies
  before proposing corrections; matching labels alone do not establish conformity.
- Check localized return-link wording and unambiguous destinations, including
  separate returns for repeated same-title occurrences. For navigation-only work,
  compare the accepted and updated visualizations: confirm the nodes themselves
  are clickable without added visual link elements or changes to labels, shapes,
  connections, styles, or layout. Report rendering-induced visual differences and
  pre-existing discrepancies instead of silently accepting or correcting them.
- For permanent diagrams, in the consumer's actual rendered entry, test each
  step-to-description link and its return link for every occurrence, including
  after navigating away and reopening the entry.
  Confirm the intended node is reached, not only the diagram container. Report
  untested behavior or unsupported viewer capabilities as unresolved findings.
  Structural validator success cannot prove label equality, semantic correspondence,
  or browser interaction.
- Confirm the SVG exists, is non-empty, legible, unclipped, unambiguous, and minimizes crossings.
- Review [edge-label placement](#edge-label-placement) against canonical meaning,
  then at a readable zoom: confirm endpoint labels can be read together with the
  relevant source or destination node without following the connection across
  the diagram. Check all labels for legibility and arrowhead labels for overlaps
  with nodes, connections, and other labels. Do not change a label's semantic
  association merely to improve the layout.
- For permanent authorship, keep source and derivative consistent after Markdown consolidation; regenerate the derivative from the accepted source when the source itself needs no change.
- For permanent diagrams, use the configured source and visualization extensions, keep every required component under one stem, and embed the visualization exactly once in Markdown. Never embed the maintenance source.
- For consistency, render to a unique temporary SVG with identical options and compare bytes. A renderer upgrade that changes output requires coordinated regeneration and visual review, not mixed versions. It grants no authority to replace files: the affected set must be covered by the closed grill, or the grill must resume before permanent writes.
- Any semantic choice stops the affected work and returns to the human through `grill.md`, including during a temporary export. Follow that guide's qualification and closure requirements; a decision about an export does not authorize permanent wiki corrections.
